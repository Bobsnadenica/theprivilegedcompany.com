A practical starting point

saml2aws,simply explained.

You sign in to your company. saml2aws gets temporary AWS credentials. The AWS CLI uses those credentials to run your commands.

Accounts vs profiles First setup Everyday use Common questions

What does it actually do?

saml2aws is a command-line login tool. It connects a company’s SAML sign-in to AWS. SAML 2.0 is a standard for passing proof of a login between systems. Your identity provider (IdP) is the service that handles your company sign-in.

  1. Sign inUse your company login and complete MFA when required.
  2. Get temporary accesssaml2aws exchanges SAML proof for credentials through AWS STS.
  3. Run AWS commandsThe AWS CLI reads those credentials from your chosen profile.

Your company must already support this SAML login flow and give you an AWS role. If its instructions use IAM Identity Center with aws sso login, follow that flow instead. AWS’s SSO setup guide.

Account ≠ profile

Think of the saml2aws account as a saved sign-in recipe and the AWS profile as a named drawer for AWS settings and credentials.

NameWhat it meansOur example
saml2aws accountA local login configuration: provider, URL, username and destination profile.company-login
AWS profileA local name AWS tools use to find credentials and settings.work-dev
AWS accountThe actual AWS environment containing resources, identified by 12 digits.123456789012 (fictional)
IAM roleThe identity you assume, with permissions for what you can do.Developer
The names can match, but they do not have to. Here, company-login puts credentials into work-dev. Naming a profile admin would not give it admin permissions.
saml2aws login --account company-login --profile work-dev
aws sts get-caller-identity --profile work-dev

--account (or -a) chooses the sign-in recipe. In saml2aws, --profile (or -p) chooses where credentials are saved. In aws, --profile chooses which profile to use.

Your first setup

Example: you want command-line access to your company’s development environment. Use your team’s real provider, login URL and assigned role; the names below are examples.

  1. Install the two tools

    On macOS with Homebrew already installed:

    brew install saml2aws awscli
saml2aws --version
aws --version

    Other systems: saml2aws installation · AWS CLI installation.

  2. Save your login recipe once

    saml2aws configure --account company-login --profile work-dev

    Follow the prompts. Use the provider and AWS SAML application URL supplied by your team, your work username and the required MFA option. Keep work-dev as the AWS profile for this example.

    Set a default region for AWS commands (replace this with your team’s region):

    aws configure set region eu-west-1 --profile work-dev

  3. Log in

    saml2aws login --account company-login --profile work-dev

    Complete sign-in and MFA. If asked to choose a role, select your assigned development role. The credentials are saved locally and expire later.

  4. Check who you are, then use AWS

    aws sts get-caller-identity --profile work-dev

    Example output (fictional):

    {
  "UserId": "EXAMPLE:your-session",
  "Account": "123456789012",
  "Arn": "arn:aws:sts::123456789012:assumed-role/Developer/your-session"
}

    Account identifies the AWS environment; Developer in the ARN is the role. Check that both are what you expect.

    aws s3 ls --profile work-dev

    This lists buckets if your role permits it. It does not create or change resources.

The everyday version

After setup, these are the commands you will usually need:

# Log in, or renew an expired session
saml2aws login --account company-login --profile work-dev

# Confirm the AWS account and role
aws sts get-caller-identity --profile work-dev

# Do your work (this example only lists buckets)
aws s3 ls --profile work-dev
Optional: stop typing --profile every time

In macOS/Linux bash or zsh, set it for the current terminal. This selects a profile; it does not log you in. Existing exported access keys can override profile credentials, so use a terminal without old AWS credential exports.

export AWS_PROFILE=work-dev
aws sts get-caller-identity
aws s3 ls

# Stop selecting this profile by default
unset AWS_PROFILE

A few things that trip people up

Where are the settings saved?

By default, ~/.saml2aws contains the login recipe under [company-login]. ~/.aws/credentials holds temporary keys and a session token under [work-dev]. ~/.aws/config holds settings such as region under [profile work-dev]. The ~ means your home folder.

Let the tools manage credentials. Do not paste them into code or commit them to Git. AWS configuration file reference.

Do I also need to run aws configure?

You do not need to enter permanent access keys for this flow. saml2aws supplies temporary credentials. The region command above only saves a setting; it does not authenticate.

My session expired. What now?

Run the login command again. To refresh even if saml2aws considers the credentials valid:

saml2aws login --account company-login --profile work-dev --force

The allowed session length depends on your company’s configuration and AWS role.

Profile not found, or no credentials?

Check the spelling of work-dev and complete the login step successfully. List the AWS profile names with:

aws configure list-profiles

--account company-login alone will not select an AWS profile in an aws command.

I logged in, but get AccessDenied

Authentication and permission are different. Check your account and role with get-caller-identity. If they are correct, ask your team whether that role allows the operation. Logging in again does not add permissions. See the IAM guide.

Does changing the profile name switch AWS accounts?

No. A profile name is just a local label. The role selected during login determines your AWS access. Use separate profiles for development and production, with the appropriate role in each, and verify the identity before working.
